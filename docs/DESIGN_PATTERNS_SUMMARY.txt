DESIGN PATTERNS AT A GLANCE
═══════════════════════════════════════════════════════════════════════════

1️⃣  MODELS (Objects instead of dictionaries)
────────────────────────────────────────────

Before:  team_manager_dict = {"Arsenal": "Mikel Arteta"}
After:   team = Team("Arsenal", Manager("Mikel Arteta"))

Why:     • Type safety (IDE knows what properties exist)
         • Methods (team.add_player(), team.get_squad())
         • Encapsulation (internal consistency guaranteed)
         • Relationships (Team contains Manager, Players)


2️⃣  SINGLETON (GameManager)
──────────────────────────

Before:  Teams.teams = [...]
         Managers.managers = [...]
         HumanPlayer.player_positions = {}
         (scattered state, inconsistent)

After:   game = GameManager()
         teams = game.get_all_teams()
         (single source of truth)

Why:     • One place to manage state
         • Guaranteed consistency
         • Easy to test (reset state)
         • Clear dependencies


3️⃣  REPOSITORY (Data Abstraction)
─────────────────────────────────

Before:  try:
             data = load_from_api()
         except:
             data = load_from_csv()
         (scattered in multiple files)

After:   repo = RepositoryFactory.create_player_repository()
         players = repo.get_players_by_team("Arsenal")
         (abstracted, centralized)

Why:     • Switch data sources (1 line change)
         • No duplication of try/except
         • Clear what interface you're using
         • Easy to mock for testing


4️⃣  FACTORY (Creation Logic)
────────────────────────────

Before:  team = Team("Arsenal", manager)
         # No validation, could be invalid
         match = Match(home, away, s1, s2)
         # Could be same team, no checks

After:   team = TeamFactory.create("Arsenal", "Mikel Arteta")
         # Validated, defaults applied
         match = MatchFactory.create(home, away, strategy=strategy)
         # Validated, properly initialized

Why:     • Validation before object creation
         • Centralized initialization logic
         • Easy to add defaults
         • Consistent across codebase


5️⃣  STRATEGY (Behavior)
───────────────────────

Before:  def match_day(...):  # Hardcoded logic
             for i in range(10):
                 is_goal = random.randint(0, 1)
                 # Fixed behavior
         
         # Want quick play? Copy function

After:   strategy = QuickPlayStrategy()
         match.set_strategy(strategy)
         match.simulate()
         
         # Want different behavior? New strategy class

Why:     • No duplication
         • Easy to add new types
         • Each strategy independent
         • Behavior encapsulated

DESIGN PRINCIPLES COMPLIANCE
═══════════════════════════════════════════════════════════════════════════

✓ Single Responsibility Principle (SRP)
  Each class has ONE reason to change
  • TeamFactory: How to create teams
  • RandomMatchStrategy: How random matches work
  • CSVDataSource: How to read CSV

✓ Open/Closed Principle (OCP)
  Open for extension, closed for modification
  • Add new strategies without modifying Match
  • Add new data sources without modifying Repository
  • Add new factories without modifying existing ones

✓ Liskov Substitution Principle (LSP)
  Subtypes are substitutable for base types
  • Any MatchSimulationStrategy can replace another
  • Any DataSource can replace another
  • Any Factory can replace another

✓ Interface Segregation Principle (ISP)
  Clients depend on minimal interfaces
  • MatchSimulationStrategy: only simulate() and get_name()
  • DataSource: only fetch methods
  • Factory: only create methods

✓ Dependency Inversion Principle (DIP)
  Depend on abstractions, not implementations
  • Match depends on MatchSimulationStrategy (abstract)
  • Not on RandomMatchStrategy (concrete)
  • Repository depends on DataSource (abstract)
  • Not on CSVDataSource (concrete)
